# MLY2更新競合と候補の保持期限

2026-09-15。実機への配置・起動変更は未実施。

`Run-GpuMarkerObserverLumaV2.py` の更新ガード読取失敗を、映像無効から区別した。
従来は短い競合でも `sourceSequence=0 / videoValid=false` を送り、Timingの候補を消していた。

| 入力状態 | Workerの出力 |
| --- | --- |
| 更新中でメタデータを読めない | `metadata_pending`。該当車体をpartial batchから省略し、既存のフレーム待機内で再試行 |
| 最初の失敗から期限未満で復帰 | 新しい有効画像だけ検出。未観測をマーカーなしの画像に置き換えない |
| 期限以上の失敗、または期限後の復帰 | `metadata_timeout`。既存のsequence=0無効通知で候補をリセットしてから、新しい観測を許可 |
| 明示的な映像無効、古い画像、未来時刻 | 従来の無効通知。凍結フレームも鮮度上限超過後は重複待ちにしない |
| MLY2世代変更 | 旧世代の車体へ無効通知を出してから、キャッシュと期限を消し、新世代を開始 |
| topology自体が読めない | 既知の車体を同じ期限で未観測扱い。未知のtopologyで検出しない |

保持期限は既存の `--maximum-frame-age-ms` と同じ値（既定60ms）。QPCで測定する。
画像の鮮度は別途、実際の受信QPCから同じ上限で判定する。待機時間や追加のタイマーは増やさない。
10Hzでも期限を100msへ延ばさず、期限後に最初の読み取りが成功した場合も先にリセットする。
無効通知の書き込みが失敗した場合は期限切れ状態を解除しない。

MMO1のバイナリ形式・フラグ、検出ID、レート選択、候補容量、退出枚数は変更していない。
`legacy_frames` の未観測は不在枚数を増やさず、既存の不在枚数も消さない。復帰後の有効画像で
続きを判定する。既存 `elapsed_time` のpartial batch解釈は維持し、今回は有効化しない。
期限切れと世代変更はsequence=0により両モードをリセットする。

## 診断と負荷

`marker_input_health` JSONを既存のstatus間隔（変更があるときだけ）と正常終了時に標準出力へ出す。
理由別累計、source ID、既知sequence、世代、時刻を含む。直近イベントは32件に制限し、あふれた数を
`omittedEvents` に残す。タイムアウト通知のsequence=0は明示的なリセット要求であり、
「受信映像の実フレーム番号が0だった」という意味ではない。

保持するのは車体ごとの小さなメタデータと期限。追加の画像コピー、GPU検出、全フレーム保存はない。
追加の辞書参照・状態更新・診断出力分の負荷はある。実運用の競合頻度・CPU負荷は未測定。
起動元でWorker stdoutを保存していない場合、終了後の診断履歴は保証しない。

## 検証

- Worker実ループを含むメタデータ試験12件：短い競合、期限後復帰、書込失敗、2台中1台の失敗、
  topology読取失敗、世代変更、凍結、重複、切断、QPC巻き戻り、診断上限。
- 関連Python試験97件が成功（marker系52件、Luma Observer系45件）。
- Timing側の録画検証で50/40/33/25/20/15/10Hz × 2候補モード × 短い競合/期限切れの28件が成功。
  5ms競合は基準の通過数・確定位置を維持。80msの未観測は対象候補を破棄し、推定通過を作らない。
- 隔離したWindows MMO1に実Writerで12batchを送り、実Timingで短い競合後の通過1件と、
  期限切れ候補の不採用を確認。本番マッピング・実車・Relayには接続していない。
